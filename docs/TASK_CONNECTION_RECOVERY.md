# 手机任务连接与控制恢复

App 内的暂停、继续、取消按钮与通知栏共用 `TaskConnectionService`。控制请求只在电脑确认后更新任务状态；手机没有收到确认时，保留本任务的待处理控制。

## 断线与连续操作

- 每个任务同时只提交一个控制请求。连续点击相同操作会合并；已有请求处理完后，再处理最新操作。
- 取消优先。取消尚未确认时，后续暂停或继续不会覆盖它；旧暂停响应也不能清掉新的取消请求。
- HTTP 超时、响应无法解析、408、429 或服务器错误后，等待约 2.5 秒重新连接进度流。取得当前任务的新快照后，再决定是否需要重试。
- 如果新快照显示任务已经暂停，待处理的暂停请求直接结束；继续请求同样先核对任务已离开暂停状态，避免确认回包丢失后重复操作并显示错误。
- 明确的客户端错误会结束对应请求，并显示后端原因。任务结束、切换或被关闭后，旧请求回调不能修改新任务的待处理控制。
- 重连先读取当前任务快照，再处理保留的控制。事件游标只会向前推进；服务器主动关闭连接时也会尝试恢复。

这里的自动重试只允许暂停、继续、取消。草稿准备、发送批准、邮件发送、路线分享和仅核验结果继续使用各自原有接口与约束。

## 开发验证

在项目根目录运行：

```bash
./build_android.command assembleDebug testDebugUnitTest lintDebug
```

`TaskControlQueueTest` 的 14 项检查覆盖请求串行、操作合并、取消优先、旧回调、任务切换、临时与明确失败，以及用新快照处理丢失的暂停／继续确认。这些是本地 JVM 回归，实际 USB 断线与通知按钮的表现需另做真机验证。

真机检查时，可以在一个不发送内容的任务中暂时断开 USB，点击暂停或取消，恢复连接后核对最终状态。还应验证连续点击“暂停 → 取消”最终保留取消；每轮保留后端状态和手机显示记录。
