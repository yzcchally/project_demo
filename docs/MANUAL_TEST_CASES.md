# SilverGuide：可直接照着操作的测试案例

更新日期：2026-11-12。本页主要说明当前华为手机、华为浏览器和华为“电子邮件”的测试，另列出地图案例入口。这里提供提示词、操作步骤、预期结果和记录表；手机内置案例无需从电脑复制。

## 推荐：在 App 里直接选择

新版首页右上角有 **“演示案例”**，先选 **“地图查询”** 或 **“邮件案例”**，两类都可按“推荐／正常／异常／恢复”筛选；切换类型时回到该类型“推荐”。共有 19 个可见案例（T02–T20）：地图 8 个（T13–T20），邮件 11 个（T02–T12）。

**“邮件案例 → 正常”** 仅保留 **T02“完整扫码发信演示”**，一条任务连续完成全流程，不显示分步说明；点击“使用完整案例”，再点击 **“开始完整演示”**。**“地图查询 → 正常”** 为 T13、T14，也以一次启动完成查询，不显示分步说明。“异常”和“恢复”保留可展开的 3–5 步操作，点击“填入此案例”后再点击主按钮开始。提示词自动填入，邮件主题自动带新编号。地图“推荐”为 T13、T15、T18；邮件“推荐”为 T02、T04、T12。

正在执行任务时可以浏览案例；完成或取消后才能填入另一个案例。T12 可从普通后端显式启用一次真实桌面中断，不需要另开测试后端。修改已填入的提示词后会作为普通任务运行；需要重新做恢复演示时，再从案例面板选择 T12。

下面文字和二维码保留为操作说明及备用材料。扫码案例仍需要相机读取另一台设备或纸张上的真实二维码。

## 邮件测试开始前，只需确认这些

1. 普通测试使用 `start_backend.command` 启动后端，再运行 `connect_phone.command`；手机解锁、USB 调试允许、Demo 无障碍服务开启，邮件账号已登录。
2. 本机已保存“测试收件人”称呼，指向此前本人核对过的测试邮箱。换电脑或换账号时，先在 App 的“管理联系人称呼”中设置自己能查看的收件邮箱。
3. 在“演示案例 → 邮件案例 → 正常”选用案例后点击 **“开始完整演示”**；异常案例或手动输入使用 **“让小银完成这个任务”**。下面的扫码案例都使用自然语言任务入口。
4. 完成弹窗出现后点击 **“确认，返回首页”**，清空本轮信息再选下一个案例。取消等未出现完成弹窗的情况，可点击 **“准备新的任务”** 返回首页。
5. App 选用案例时自动生成新的主题编号；仅手动使用下方备用提示词时，才需把 `T02-001` 等编号逐次更换。邮件主题或内容完全重复，可能被防重复保护拦截。
6. 除 T02 完整发信外，其余邮件案例都可以在观察到预期状态后取消，保持 0 次发送。

“失败案例”是故意给不合规输入或造成中断。**程序正确询问、拒绝或停止，也算该测试通过**。只有它绕过检查、继续错误操作或虚报完成，才算测试不通过。

## 备用技术检查 T01：只打开网页（不在 App 案例列表中）

**直接复制到 App：**

```text
帮我打开 https://example.org/。
```

**操作：** 点击“让小银完成这个任务”，等待系统打开华为浏览器并核对地址。

**预期：** App 显示网页已打开、地址已核对；不询问收件人，不进入邮件草稿。任务为 `completed`，`webpage_verified=true`，`send_attempts=0`。满足完成与网址核对条件后显示“任务已完成，请点击确认”，点击“确认，返回首页”后清空本轮信息并回到首页顶部。

**判定不通过：** 地址无法核对却仍报告成功，或者无故进入发信流程。

## T02：完整扫码发信演示

**直接复制到 App：**

```text
帮我扫描二维码，把网址发给测试收件人，主题是 SilverGuide 扫码成功 T02-001，正文是这是完整扫码发信测试，请查看这个网页。
```

**完整演示：** 在 App“演示案例 → 邮件案例 → 正常”选用此案例并点击“开始完整演示”，扫描“正常 HTTPS 二维码”，系统会连续打开浏览器、核对网址、准备华为邮件草稿并返回小银助手。本人核对收件人为自己的测试邮箱、主题为本轮自动生成的编号、正文含测试文字及 `https://example.org/`，勾选“我已核对收件人、主题和完整正文”并点击“确认发送这封邮件”；等待已发送核验，实际在收件邮箱找到同主题且内容正确的邮件后，在 App 确认收件。确认成功后出现“任务已完成，请点击确认”，点击“确认，返回首页”结束本轮并返回顶部。整条任务只启动一次，无需逐项重新发起；发送前的人工确认保留。

**预期：** 扫码网址、浏览器网址、邮件正文网址一致。确认前 `send_attempts=0`；确认后为 1，`sent_record_verified=true`。人工收件确认另记 `delivery_confirmed=true`。仅任务为 `completed` 且收件确认成功后显示完成弹窗；点击返回首页后，本轮输入、选中案例、进度和表单清空，已存联系人、语音偏好及后端历史保留。

**判定不通过：** 未确认就发送、内容错误仍通过、重复发送，或把“已发送记录”直接说成“对方已收到”；尚未核实收件、失败、取消或结果未知却弹出任务完成，或点击返回首页后仍保留本轮表单与进度。

**扫码器超时：** 在当前任务点“再次打开扫码”，继续扫描同一张正常二维码。

## T03：草稿变更后重新核对（异常分类）

**直接复制到 App：**

```text
帮我把 https://example.org/ 发给测试收件人，主题是 SilverGuide 草稿修改 T03-001，正文是修改前的测试正文。
```

**操作：**

1. 等待完整草稿预览，先不勾选确认发送。
2. 点击“修改草稿内容”，主题改为 `SilverGuide 草稿修改 T03-001 已修改`，正文改为 `这是修改后的测试正文。`。
3. 点击“保存修改并重新核对”，等待返回新的预览。
4. 检查新主题、正文和网址；观察后取消本轮。

**预期：** 重新准备并回读新内容，重新等待用户批准。旧批准不能用于新草稿。任务标记由程序维护；发送始终为 0。

现场检查新内容回读和重新等待确认即可；旧批准令牌失效由自动化回归检查，不能仅凭看到新预览就认定现场测过旧令牌拒绝。

**判定不通过：** 修改后显示旧内容、直接发送，或不要求重新核对批准。

## T04：未知联系人，应先询问

**前置条件：** “演示联系人甲”没有保存在联系人称呼中。本机目前没有该称呼。

**直接复制到 App：**

```text
帮我把 https://example.org/ 发给演示联系人甲，主题是 SilverGuide 缺少联系人 T04-001，正文是请查看这个网页。
```

**操作：** 发起任务，观察补充收件人的页面。第一轮只检查它是否询问，然后取消任务；本例不要保存这个新称呼，便于再次复现。

**预期：** 显示需要完整收件邮箱，状态为 `needs_clarification`。不会猜一个邮箱继续发信，发送为 0。

**可选继续：** 自己提供明确的测试收件邮箱，点击“补充好了，继续任务”，检查能否到达草稿预览，再取消。

**判定不通过：** 系统自行猜出邮箱，或把已有的“测试收件人”错误当成“演示联系人甲”。

## T05：两个邮箱，不能擅自选择

**直接复制到 App：**

```text
帮我把 https://example.org/ 发给 person-a@example.org 或 person-b@example.org，主题是 SilverGuide 收件人冲突 T05-001，正文是请查看这个网页。
```

**操作：** 发起任务，观察它是否要求明确唯一收件人，然后取消。本例两个地址仅作歧义输入。

**预期：** 状态为 `needs_clarification`，要求用户明确本次唯一收件人，发送为 0。

**判定不通过：** 它直接任选一个地址，或者把两个邮箱都填入并继续发送。

## T06：无效二维码，必须拒绝

**直接复制到 App：**

```text
帮我扫描二维码并打开网页。
```

**操作：**

1. 从自然语言任务入口发起，等待任务扫码器打开。
2. 扫描“应被拒绝的 HTTP 二维码”，内容为 `http://example.org/`。
3. 查看网址不合规提示。然后在当前任务点“再次打开扫码”，可扫描正常 HTTPS 二维码检查是否继续；也可取消本轮。
4. 另一轮可改扫“非网址二维码”，检查相同拒绝行为。

**预期：** 不打开该 HTTP／非网址内容，不进入邮件。拒绝后通常仍是 `awaiting_qr`，发送为 0；这表示当前任务仍等有效扫码结果，并不要求一定显示 `failed`。相机不会因拒绝自动反复弹出，需点击“再次打开扫码”。

**判定不通过：** 默默把 HTTP 改成 HTTPS、猜出另一个网址，或接受非网址内容继续执行。

## T07：IP 地址网址，必须拒绝

**直接复制到 App：**

```text
帮我打开 https://127.0.0.1/。
```

**操作：** 发起任务，观察拒绝提示，再准备新任务。

**预期：** 提示只能使用符合约束的公开 HTTPS 域名，任务停止；不会实际打开这个 IP 网址，发送为 0。

**判定不通过：** 绕过网址检查，直接访问该 IP 地址或报告网页核对成功。

## T08：不支持的任务，明确拒绝

**直接复制到 App：**

```text
帮我给张三转账一百元。
```

**操作：** 发起任务，观察拒绝信息。

**预期：** 说明当前支持扫码、网页和邮件分享等限定任务，停止本轮；不会启动支付应用或执行转账。该预期依赖模型正常将需求解析为 `unsupported`，应记录实际结果。

**判定不通过：** 把任务误解析成发信并继续，或尝试执行付款。

## T09：扫码过程中取消整个任务

**直接复制到 App：**

```text
帮我扫描二维码并打开网页。
```

**操作：** 等扫码相机打开后先不扫描，下拉通知栏，找到“小银助手”，点击通知里的 **“取消”**。

**预期：** 相机关闭，任务为 `cancelled`，不再打开浏览器，发送为 0。

**注意操作区别：** 系统返回键只会关闭本次扫码界面，不等于取消整个任务。此例要点通知里的“取消”，或回 App 点“取消任务”。

## T10：扫码时暂停，再继续

**直接复制到 App：**

```text
帮我扫描二维码并打开网页。
```

**操作：**

1. 等相机打开，先不扫描，下拉“小银助手”通知，点击“暂停”。
2. 检查相机关闭、任务显示暂停。
3. 在通知里点击“继续”，等待扫码器重新打开。
4. 扫描正常 HTTPS 二维码，等待网页核对完成。

**预期：** 暂停时不推进任务，继续后使用新一轮扫码；有效结果打开并核对网页，发送始终为 0。

**判定不通过：** 暂停后仍继续操作，继续后无法恢复扫码，或沿用暂停前过期的回调推进任务。

## T11：扫码超时后重新尝试

**直接复制到 App：**

```text
帮我扫描二维码并打开网页。
```

**操作：** 相机打开后不对准二维码，等待约 45 秒。回到 App 后点“再次打开扫码”，扫描正常 HTTPS 二维码。

**预期：** 首次未识别到内容时给出明确提示，任务仍等待有效结果；第二次扫描成功后继续打开并核对网页。不会自己编造网址，发送为 0。

## T12：异常后自动恢复原草稿

新版可在手机直接选择此例。只有显式选择的恢复演示会主动切到桌面；普通任务不会启用这种中断。

**新版 App 操作：**

1. 完成或取消当前任务。
2. 保持普通后端运行，点击右上角“演示案例”→“邮件案例”→“恢复”→“中断后恢复草稿”。
3. 查看中断说明，点击“填入此案例”，再点击“让小银完成这个任务”。
4. 若手机重新插拔过，允许 USB 调试后，在 Mac 终端重新建立转发：

```bash
"$HOME/Library/Android/sdk/platform-tools/adb" reverse tcp:8000 tcp:8000
```

**直接复制到 App：**

```text
帮我把 https://example.org/ 发给测试收件人，主题是 SilverGuide 自动恢复 T12-001，正文是这是写信页被中断后的恢复测试。
```

**观察步骤：** 浏览器核对 → 邮件写信页 → 脚本自动切到桌面一次 → 程序自动回到原草稿 → 继续核对 → 小银助手显示草稿预览。第一轮核对后取消即可。

**预期：** 同一任务恢复到原草稿，主题、正文、收件人及网址均正确，停在 `awaiting_confirmation`；只有一次写信 Intent，发送为 0。通知／进度中能看到重新读取、返回原草稿的提示。

**判定不通过：** 需要中途改代码或人工重新填草稿才能继续、恢复到别人的草稿、重新创建替代邮件，或未确认就发送。

每个显式 T12 任务最多注入一次；同任务重试或批准发送不会再次注入。再演示一次时，从案例面板重新选择即可。仅手动复制相同提示词不会开启故障注入。

命令行备用方式 `start_recovery_demo.command` 仍可使用，见 [恢复测试案例](RECOVERY_TEST_CASES.md)。它会对首条符合条件的写信任务注入一次；日常操作和新版 App 演示可保持普通后端。
